# LiveControl 检查结果与修补计划

检查日期：2026-09-30。目标项目：`G:\产品\LiveControl`。
本轮为检查与规划，没有修改 LiveControl 源码、覆盖安装包、启停直播服务或注册管理员任务。

## 结论与范围

当前维护版本为 Electron 33.4.11 + CommonJS 主进程 + Material Web 2.5 + esbuild 渲染构建；WPF 为 README 明确标注的不维护旧版。现有技术栈可以管理 Python 硬件采集和独立管理员温度桥，无需重写桌面壳。

先修服务生命周期与版本发布，再集成温度桥。否则桥接器接入后会继承重复启动、状态误报、端口强杀和控制台重开丢失管理关系的问题。

修补保持 LiveControl 的现有 Material 风格；直播边框继续沿用已有设计系统与硬件接口，不改变其排版。

## 温度桥集成设计

### 用户体验

在“硬件状态”服务增加“CPU温度”状态和设置入口：FanControl目录、自动启动温度桥、启动/重试、诊断。展示未启动、等待管理员授权、启动中、已连接、数据过期、读取失败、依赖缺失；附最近更新时间和采集来源。

用户打开 LiveControl 后，先检测已有 Python 服务和有效温度数据。启用自动启动且没有健康桥时，由 LiveControl 触发 Windows UAC，启动独立只读桥。已有健康桥直接复用，不重复弹 UAC。取消 UAC 时显示“授权已取消”，其余硬件指标继续显示；自动流程不反复弹窗，重试由用户操作触发。

开机自启 LiveControl 与启动其他直播服务分开。启动温度桥不要求“一键开播”；开机后第一次需要权限时会出现 UAC。全自动免交互启动需要另行设计 Windows 高权限任务，本阶段不默认注册它。

### 对接链路

`LiveControl 普通权限主进程 → 固定桥启动适配器 → UAC → CPU只读桥 → cpu-temperature.json → Python7790 → 直播边框`

1. 保留 `phase-hardware` 的 `/healthz`、`/state` 接口；由主进程查询并向界面推送硬件/CPU细分状态，避免将 Electron renderer 新增直连7790及CSP变更作为必要条件。
2. CPU桥复用现有 net10.0 组件与 FanControl 自带监控库，只读 CPU 温度。LiveControl 自身继续普通权限。这个权限分离也符合 [Microsoft 官方建议](https://learn.microsoft.com/en-us/windows/win32/secbp/running-with-administrator-privileges)。
3. 增加 `hardware-manager.js` 管理硬件采集、`cpu-bridge.js` 管理桥接权限和健康。提升权限时只启动固定程序/固定参数，校验实际程序、依赖目录和输出位置，不暴露通用管理员命令 IPC。
4. 参数含中文、空格时保持完整；UAC进程启动成功后，等待新鲜CPU数据才标记已连接，不能只凭 PowerShell返回0或进程名称判断成功。现有重复检测仅检查进程名，需改为项目实例身份与心跳判断。
5. CPU桥当前输出2秒刷新，消费者8秒过期；在状态输出增加桥版本、实例标识/PID、数据时间和错误类别，并保持旧消费字段兼容。健康≠一定取得有效CPU温度，应分别展示“进程运行/传感器可用”。
6. 普通权限无法可靠结束管理员进程，不能复用现有 taskkill 逻辑。为本桥增加受限本机停止/重启控制协议：只能退出或重启当前绑定实例，核对用户、实例与命令白名单，不提供命令执行能力；受限命名管道为候选，集成时做权限验证。未完成该协议前只提供启动/诊断和明确不可用的停止状态。
7. 关闭 LiveControl 保持现有“服务继续运行”的行为；重开识别已有实例。一键下播只处理直播链路，硬件与桥按用户设置决定是否保留，避免无意义地重新请求管理员授权。
8. FanControl路径先识别已运行进程/保存配置，允许手动选择；检查 `.NET10` 或发布自包含桥、所需 DLL 和库兼容性。CPU桥发布与依赖清单必须落在安装包/外部资源路径，不能从 asar 内直接执行。应用内显示可操作的缺失依赖提示。

### 包含的代码入口

`services.js`（目录配置和服务身份）、`hardware-manager.js`/`cpu-bridge.js`（新增能力）、`main.js`（启动接入/IPC）、`preload.js`（最小白名单）、`config.js`（迁移）、`renderer/renderer.js`（状态/设置）、`renderer/style.css`（现有M3 token）、`package.json`（资源与构建）。

桥组件在 OBS 工程中维护；LiveControl 只负责启动和管理，Python负责硬件数据，边框负责显示。避免将采集逻辑复制进多个项目。

## 实施顺序与验收

1. **建立基线与无干扰检查。** 保存源码与当前配置的可回滚基线；确认源目录、安装目录和构建版本，建立纯单元测试入口。替换目前会真实启停弹幕服务的默认 selftest；保留显式标明副作用的人工集成检查。
2. **修管理基础（P0/P1）。** 去掉按端口强杀，补服务身份、操作锁和状态机；修错误完成提示、开关状态和显式开/关播动作；配置迁移和原子保存。先用模拟进程、HTTP和配置文件验证，不接触直播。
3. **接入温度桥。** 普通权限主进程启动/复用只读桥、UAC结果、数据新鲜度、可选依赖、目录设置与日志；实现受限生命周期控制，再开放重启功能。验证已有桥不会被替换或重复启动。
4. **健全与整理（P2）。** HTTP/WS统一生命周期、日志上限、泛光绑定、窗口状态、OBS连接释放、IPC来源和入参校验。拆分 main 的窗口/托盘/OBS/IPC职责，使用 JSDoc类型检查与配置schema，不强行同时改换框架。
5. **完整构建发布。** 主窗/浮窗重打包，桥及资源打入正确位置；校验 asar 的服务与版本、路径包含中文/空格的便携版和安装版。选择可切换时机后更新实际运行版，回滚使用之前的发布件和兼容配置。

关键验收场景：

- 连续点击启动/重启只产生一个实例；停止中不启动；旧退出事件不覆盖新实例。
- 已有弹幕/硬件服务时打开或退出控制台，直播不中断；陌生端口占用不被结束。
- CPU桥已运行时无UAC；首次启动有UAC；取消/超时/缺失DLL均准确提示，不阻断RAM/GPU或直播服务。
- 断开/退出桥后8秒内显示过期，恢复后重新取得真实CPU温度；0°C被按合法数据处理，不用假值填补。
- 控制台重开和电脑重启后正确识别实例与配置；显示的发布版本能追溯实际构建。
- start/stop按钮在相反状态不能触发反向直播操作；组件开关的真实点击与持久化一致。
- 旧配置升级保留用户设置，合法数字0不丢失；损坏或保存失败能诊断并恢复。
- 日志高频持续输入、WS掉线重连、API挂起、主窗/浮窗交互长期运行，无无限DOM增长和叠加轮询。

Electron依赖升级作为单独发布任务，按官方兼容变更逐版本验证；IPC来源校验等遵照 [Electron安全文档](https://www.electronjs.org/docs/latest/tutorial/security)，不与第一批服务生命周期修补混在一个无法定位回归的大改中。
